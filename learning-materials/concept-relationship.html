Agent · LLM Context · Skill

Agent 是"做事的方式"（带闭环），上下文是"做事时的输入"（一次能看见的全部），Skill 是"做事的方法论"（按需加载的流程包）。三者一起，构成了现代 LLM 应用的内核。

一张图看清三者关系

一句话总结三者

  • Agent：做什么、按什么节奏做。
  • 上下文：做的过程中"看得见"什么。
  • Skill：在合适场景下，把方法论"塞进"上下文。

三个一起跑的场景

场景 A · 单轮问答

用户问"上海今天要带伞吗"

Skill：没有命中任何 Skill（普通问答不需要方法论）。

上下文：只包含系统提示 + 用户消息。

Agent：因为这是个一次性回答（不需要看自己行动的结果），其实走的是开环模式 —— 这也是为什么"带伞"这种问题用不用 Agent 框架差别不大。

场景 B · 单 Skill 介入

用户："帮我按团队规范提交代码"

Skill：commit-style-enforcer 被命中，加载到上下文。

上下文：系统提示 + Skill 全文 + 当前 git diff + 用户消息。

Agent：按 Skill 规定的"先校验 → 再 commit"流程跑，跑完报告结果。Skill 给出方法，Agent 负责执行与节奏。

场景 C · 多 Skill + 工具 + 长上下文

用户："帮我调研 X 技术，输出对比报告"

Skill：research-workflow（调研流程）+ report-template（报告模板），按顺序命中。

上下文：系统 + 两个 Skill + 工具结果（搜索、读取网页）+ 检索片段 + 用户消息。窗口可能跑到 50K+ token。

Agent：循环几十轮：搜索 → 读 → 摘要 → 再搜索 → 写草稿 → 自检 → 给用户。Skill 负责"按什么规范"，Agent 负责"跑几轮、什么时候该停"。

三者各负责什么 / 不负责什么

概念负责不负责
Agent 决策节奏、循环次数、何时停、是否调用工具 记忆（每次推理都是失忆患者）；工具本身的能力上限
上下文 把这一轮"看得见的信息"完整地交给模型 决定哪些信息"应该被看见"（这是上层调用方的责任）
Skill 把团队 / 个人经验沉淀成可复用文档 保证每次都被调用（依赖触发机制）；代替工程实现

常见的混淆与反模式

反模式 1

把"调用 Skill"当成万能解药

期望只要写了 Skill，AI 就一定会在该用它的时候用它。事实：Skill 触发依赖 read_when 与请求的语义匹配。如果你的 read_when 写得含糊，AI 会频繁误触发或漏触发。

修正：把 read_when 写成"用户会怎么问"，而不是"它内部做了什么"。

反模式 2

把"上下文管理"完全交给 Agent

认为只要 Agent 够聪明，它会自己管理 token。事实：Agent 通常不会主动做截断 / 摘要，token 越界它就崩了。

修正：在系统层做上下文管理（窗口限制、摘要、RAG），把"已清理过的上下文"交给 Agent。

反模式 3

把"Skill 写得越详细越好"

把所有规则都写进 Skill，导致单次加载就吃光上下文窗口。事实：Skill 是被加载进上下文的，越长越挤。

修正：Skill 只写"必要规则 + 边界 + 自检"。详细信息放 references/ 子目录，按需读取。

自检题

点击"显示答案"看解释。

1. Agent 跑了几十轮后窗口满了，下面哪种说法最准确？

  1. Agent 应该自动决定丢掉哪些历史
  2. 是上下文管理出了问题，应该在系统层做摘要/截断
  3. 换更大的模型就行
  4. 让 Skill 自动瘦身
答案：B。上下文管理是系统层的责任。Agent 不擅长"主动忘掉事情"。设计时就要把"清理上下文"的流程做进去。

2. 一个项目级 Skill 应该放在哪里？

  1. 用户家目录 ~/.workbuddy/skills/
  2. 项目仓库内的 .workbuddy/skills/<name>/SKILL.md
  3. 随便一个 markdown 文件都行
  4. 必须打包成 .zip
答案：B。项目级 Skill 放在仓库内的 .workbuddy/skills/<name>/，随仓库分发，团队共享。A 是用户级 Skill 的位置。

3. 下面哪个不是三概念协作的必要条件？

  1. 有一个清晰的目标
  2. 上下文足够装下当前轮次的关键信息
  3. 有可用的 Skill 或方法论
  4. 每次都要同时用上三者
答案：D。三者不是必须同时出现。简单问答用不上 Agent 框架，普通任务也用不上 Skill。三者各按需取用。
