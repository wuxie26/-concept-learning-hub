Skill / 技能

Skill · Capability Package · Reusable Procedure

把"何时该调、按何流程做、需要哪些知识"打包成可复用模块的封装，让 AI 在合适的场景自动加载并执行。

预计 10 分钟 入门难度 AI · 模块化

一句话三连

是什么 What

一个 SKILL.md + 可能附带脚本 / 资源的目录。它告诉 AI："这种场景按这套流程办"。

为什么重要 Why

把"经验"从一次性 prompt 升级为可复用资产。人和团队都可以基于 Skill 共享方法论。

怎么写 How

YAML frontmatter 描述触发场景，Markdown 正文描述流程与质量基线，必要时附带脚本。

核心机制：触发 + 流程 + 知识 三合一

Skill 不是一段 prompt，而是一个能力包。它把三件事打包在一起：

Skill 是怎么被"调起来"的？

  1. AI 看到当前对话 / 请求。
  2. 把所有可用 Skill 的 read_when 字段（触发关键词 / 场景描述）与请求做匹配。
  3. 命中后将 Skill 的正文加载到上下文，按其规定的流程执行。
  4. 执行完毕后上下文被清理，Skill 不再"常驻"。
Skill 不是"自动运行的后台程序"，而是"按需加载的方法论文档"。它有边界、有人类审核的责任、有版本。

两类 Skill：User-level vs Project-level

  • User-level：放在 ~/.workbuddy/skills/，跨项目共享，例如"我的写作风格偏好"。
  • Project-level：放在仓库内的 .workbuddy/skills/，随仓库分发，例如"本项目的部署流程"。

冲突时项目级优先，因为它对当前项目更具体。

三个递进示例

L1 · 最小

最简 Skill：只定义触发 + 一段流程

---
title: friendly-greeting
summary: 用户开头打招呼时给一个温暖、有名字感的回复
read_when:
  - 用户说"你好"、"hi"、"在吗"等寒暄
---

# friendly-greeting

## 流程
1. 先用一个问句回应（确认对方意图）。
2. 如果知道对方名字，用名字招呼。
3. 主动问"今天想做什么"。

## 不要
- 不要长篇大论地自我介绍。
- 不要主动推销功能。

这个 Skill 只有 30 行，但已经定义了何时被调 + 怎么做。

L2 · 实用

带资源 / 脚本的 Skill：commit 风格统一器

commit-style-enforcer/
├── SKILL.md           # 主流程描述
└── scripts/
    └── check.py       # 自动跑校验

SKILL.md 描述规则（提交信息格式、受影响文件清单），scripts/check.py 在每次 commit 前自动跑。AI 收到"帮我提交"请求时，会先看 SKILL.md，再用脚本去校验。

这是 Skill 真正强大的地方：知识 + 流程 + 可执行工具合一。

L3 · 系统级

项目级 Skill：把团队方法论装进仓库

一个团队的"代码评审 checklist"以前散落在 wiki、Slack、口头相传。新人入职要花一周才能摸清。

把它做成项目级 Skill：放在仓库的 .workbuddy/skills/code-review/SKILL.md。从此：

  • 任何 AI 接到"帮我 review 这个 PR"时，会自动按这个清单来。
  • 团队 review 风格被版本化，可以一起迭代。
  • 新人 PR 第一次就能被同一个标准检查。

常见误区 / 反直觉点

✕
"Skill 越多越好"

反了。Skill 多了会互相冲突、互相触发、互相覆盖上下文。一个项目通常 3 ~ 8 个 Skill 就够。超过这个数量，要先合并 / 重构。

✕
"Skill 就是一段高级 prompt"

不对。Skill 是文档 + 触发 + 资源 + 责任边界的总和。一段 prompt 没有触发场景、没有版本、没有负责人；Skill 有。

✕
"Skill 写好就万事大吉"

Skill 是会过期的。API 变了、流程改了、工具换名了，Skill 里的旧指令会让 AI 做出错误动作。要把 Skill 视作代码一样维护。

✕
"Skill 越大越全越好"

不对。Skill 是被加载进上下文的，写得太长会挤占对话窗口；写得事无巨细会让 AI 在简单任务上过度反应。Skill 是手术刀，不是锤子。

自检题

点击"显示答案"看解释。

1. 下面哪一项不是Skill 的必备要素？

  1. YAML frontmatter（title / summary / read_when）
  2. 流程描述的 Markdown 正文
  3. 对应的 Python 脚本
  4. 触发场景的明确说明
答案：C。脚本是可选资源。许多 Skill 只有 SKILL.md 就够了。必备是触发条件 + 流程描述。

2. 项目级 Skill 和用户级 Skill 同时匹配了一个请求，谁优先？

  1. 用户级（更个人化）
  2. 项目级（更贴合当前项目）
  3. 后注册者优先
  4. 名字长的优先
答案：B。项目级 Skill 优先，因为它是为当前项目专门写的；用户级 Skill 是兜底 / 跨项目的偏好。

3. 下面哪种做法最符合"好 Skill"的标准？

  1. 把所有可能用到的方法都写进 SKILL.md，越全越好
  2. 流程清晰、边界明确、含质量自检清单
  3. 和 prompt 一样随手写，写完不维护
  4. 只描述"要做什么"，不写"不要做什么"
答案：B。好 Skill 像好代码 —— 单一职责、清晰流程、有自检、有"不要做什么"的边界说明。

与相邻概念的边界

概念核心区别
Skill vs PromptPrompt 是一次性输入；Skill 是带触发 + 资源 + 维护责任的可复用封装。
Skill vs SubagentSubagent 是"另一个 AI 实例"被调度；Skill 是"主 Agent 按既定方法办事"的指南。
Skill vs WorkflowWorkflow 是预定义步骤序列；Skill 让 AI 自主决定要不要 / 怎么跑这些步骤。
Skill vs PluginPlugin 通常指 MCP 工具 / 第三方连接器（Connector），强调外部能力；Skill 是方法论文档，强调流程与判断。
