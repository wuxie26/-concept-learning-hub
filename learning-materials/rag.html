RAG / 检索增强生成

Retrieval-Augmented Generation · Grounded LLM

一种让 LLM 在回答前先去外部知识库"查一下"的架构。检索到的内容会被拼进上下文，从而让模型能基于"事实"而不是"训练记忆"作答。

预计 10 分钟 进阶难度 LLM 应用 · 工程化

一句话三连

是什么 What

一个"先检索、再生成"的两阶段流程：把检索到的相关片段塞进上下文，让模型基于真实资料回答。

为什么重要 Why

同时解决 LLM 的三大痛点：知识陈旧、幻觉瞎编、私有数据不可见。

怎么实现 How

文档切块 → 向量化 → 入向量库；查询时把问题也向量化 → 检索 top-k 相似块 → 拼进 Prompt → LLM 生成。

核心机制：索引 + 检索 + 生成

RAG 的整个工作流可以分成两段：离线索引（建库）和在线问答（检索 + 生成）。

1. 文档切块（Chunking）

把长文档切成几百字左右的小块。切得太长会模糊语义、太短会失去上下文。常见策略：固定窗口、重叠窗口（overlap）、按段落 / 标题切、按语义切。

2. 嵌入（Embedding）

每个块用嵌入模型转成一个高维向量（如 1536 维）。向量代表"这块文字的语义"。两个向量在空间中"近"代表它们语义相关。

3. 检索（Retrieval）

用户提问也嵌入成向量，去向量库里找最相似的 top-k 个块（默认 k=3 ~ 10）。检索方法常用余弦相似度或 ANN 索引（HNSW / IVF）。

4. 增强生成（Augmented Generation）

把检索到的 top-k 块拼进 Prompt："请根据以下资料回答问题：[资料 1]\n[资料 2]\n...\n问题：xxx"。LLM 基于真实资料生成回答，减少幻觉。

RAG 的本质不是"用 LLM 做搜索"，而是"把搜索结果当作上下文喂给 LLM"。它把"信息检索"和"自然语言生成"两件事优雅地拼在一起。

三个递进示例

L1 · 最小

FAQ 客服机器人

把公司常见问答做成文档索引。用户问"如何退款"，检索到退款的 3 段说明，模型据此生成礼貌、完整的答复。

用户：怎么退款？
检索 top-3：
  [1] "退款需在 7 天内提交申请 ..."
  [2] "退款流程：登录 → 订单 → 申请退款 → 等待审核 ..."
  [3] "退款会在 3 个工作日内原路返回 ..."

Prompt：
  你是一名客服。请根据以下资料回答用户问题。
  ---资料---
  [1] ...
  [2] ...
  [3] ...
  ---用户问题---
  怎么退款？

LLM：您可以在订单页提交退款申请，7 天内有效，
      一般 3 个工作日原路返回。
L2 · 中等

企业内部文档问答

把 Wiki、Confluence、产品手册全部索引。员工问"项目 X 上线流程是什么"，系统找到相关流程文档并总结。

关键工程点：

  • 权限过滤：检索结果要按用户权限过滤（不能把高管文件给普通员工看）。
  • 元数据：每块带"部门 / 时间 / 来源 URL"，便于引用与可信度评估。
  • Re-rank：粗排后用更强的模型精排，提高 top-k 准确率。
L3 · 复杂

Agentic RAG：让 Agent 自己决定要不要检索

传统 RAG 是"先检索再回答"。Agentic RAG 把检索做成一个工具，让 Agent 自主决定：

Agent 思考流程：
  Q: 2025 财年 Q3 营收是多少？
  ├─ 思考：需要最新数据，先去知识库查
  ├─ 行动：tool_call(retrieve_kb, "2025 Q3 营收")
  ├─ 观察：返回 3 段，最相关的是 Q3 财报披露
  ├─ 思考：信息够了，整理回答
  └─ 回复：2025 财年 Q3 营收为 12.3 亿美元（同比 +18%）。

后续用户问"那 Q4 呢？"
  ├─ 思考：用户接着问，可能还要查
  ├─ 行动：tool_call(retrieve_kb, "2025 Q4 营收")
  └─ ...

Agentic RAG 让模型在不确定 / 信息不足时主动检索，避免每次都强行检索造成的浪费。

常见误区 / 反直觉点

✕
"RAG = 把文档贴进上下文"

不完整。RAG 的核心是按相关性检索。如果只是把所有文档塞进上下文，既贵又乱，还会让 lost-in-the-middle 更严重。

✕
"embedding 越好，RAG 效果越好"

不必然。embedding 之外还有三个常被忽视的因素：切块策略（语义边界）、查询改写（用户问得不清楚时改写）、重排序（粗排后精排）。

✕
"RAG 能 100% 解决幻觉"

不能。RAG 减少幻觉，但当检索不到相关资料、或资料本身就错，模型仍可能胡编。RAG 是"降低概率"，不是"消除"。

✕
"RAG 一定会变贵"

不一定。RAG 相比长上下文，单次 token 更少，单次调用反而更便宜。贵的地方是向量库存储 + 嵌入调用，但要换的是"质量 / 时效 / 私密性"。

自检题

点击"显示答案"看解释。

1. RAG 的"检索"阶段，召回的是？

  1. 整篇文档
  2. 预先切好的、与问题最相似的 top-k 个文档块
  3. 模型的内部知识
  4. 随机的几个片段
答案：B。RAG 检索的是切块后的片段而非整文档，目的是减少无关信息、节省 token、提高相关性。

2. 为什么 RAG 特别适合"私域 / 最新"场景？

  1. 因为 LLM 不能联网
  2. 因为检索源（向量库）可以随时更新、且不受训练数据限制
  3. 因为 RAG 比 fine-tuning 便宜
  4. 因为 RAG 用更小的模型
答案：B。向量库可以每天 / 每小时重建，私域文档也能直接索引，无需重新训练模型。这是 RAG 最大的工程价值。

3. Agentic RAG 与传统 RAG 最关键的区别是？

  1. 用了更强的 embedding
  2. Agent 可以自主决定要不要检索 / 检索几次 / 检索什么
  3. 不用向量库
  4. 完全离线
答案：B。Agentic RAG 把检索做成"可调用工具"，由 LLM 在循环里自主调度，避免"每次都硬检索"造成的浪费与噪声。

4. 下面哪个不是RAG 的典型环节？

  1. 文档切块
  2. 向量嵌入
  3. 梯度反向传播
  4. 相似度检索
答案：C。RAG 不训练模型，"梯度反向传播"是模型训练的概念。RAG 是纯推理时的检索 + 拼接 + 生成。

与相邻概念的边界

概念核心区别
RAG vs 长上下文长上下文直接把文档塞进 LLM；RAG 只塞"相关的几段"。前者贵、后者精。
RAG vs Fine-tuningFine-tuning 把知识"焊进模型权重"；RAG 把知识"外挂"在向量库。前者改模型，后者不改。
RAG vs 提示词工程提示词工程优化"如何问 LLM"；RAG 还优化"给 LLM 喂什么"。前者是话术，后者是数据流。
RAG vs 搜索引擎搜索引擎返回链接让用户自己读；RAG 直接消化后给"答案"，用户不必点链接。
